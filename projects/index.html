No. 001 · Flagship · 2026-07-13

Roundtable

Agentia visibilis

AI Agent · Product Systems · Next.js · TypeScript

A visible AI dev squad workbench: plan a task, run agents in parallel, review outputs, preserve files, diffs, previews, and decisions.

GitHub ↗

Problem

Most multi-agent coding tools hide the actual work. A prompt goes in, a long answer comes out, and the user cannot easily see who planned, who implemented, what changed, or why a review passed.

My Role

  • Shaped the product concept around a visible AI dev squad and persistent workbench
  • Built across the Next.js app, server action layer, CLI workflows, and local/Postgres storage paths
  • Designed the review/fix loop so failed work is bounded instead of becoming an infinite agent loop
  • Added developer checks around type safety, tests, safety scanning, and deterministic local demos

Product Decisions

  • Made the run itself the product: plans, handoffs, files, diffs, previews, and decisions stay attached to the mission
  • Used a dependency-aware task graph so independent work can run in parallel while blocked tasks wait for prerequisites
  • Kept a zero-key local-dispatch adapter so the product can be demoed and tested without external model credentials

System Design

Next.js 15 + React + TypeScript, tRPC/REST/CLI over one shared action layer, local JSON or normalized Postgres storage, NextAuth for auth, and pluggable agent adapters for local CLIs, E2B, MiniMax, or deterministic CI.

Outcome

A working agent workbench with planner, implementers, reviewer, architect, fixer roles, visible artifacts, bounded fixer rounds, and safety checks before agent output lands.

Reflection

The strongest product insight here is that agent autonomy needs product surfaces for trust: users need to inspect the plan, the artifact, and the review state, not just receive a polished final answer.

No. 002 · Research · 2026-07-08

Agent Memory Benchmark

Memoria communis

AI Memory · Evaluation · Python · LLM Systems

A benchmark for shared-memory LLM systems, testing whether multiple agents can preserve, update, and retrieve memories without silent loss.

GitHub ↗

Problem

Modern memory benchmarks mostly assume one agent owns its own memory. Real AI work is moving toward shared memory across Claude, ChatGPT, Codex, custom agents, MCP tools, and product-specific runtimes. That creates a different question: when multiple agents write to and read from the same memory layer, do memory systems still preserve the details that matter?

My Role

  • Designed the v1 benchmark suite for non-trivial multi-agent shared-memory behavior
  • Built Python runners, case generators, system adapters, and programmatic judges
  • Compared baselines against mem0 and documented decisions, limitations, and findings
  • Produced reproducible cases, result analysis scripts, and charts for benchmark writeups

Product Decisions

  • Moved beyond atomic one-fact memories because they do not discriminate modern systems
  • Focused v1 on split intake, compound updates, surgical edits, and cross-memory updates
  • Used programmatic scoring where possible to reduce LLM-as-judge ambiguity

System Design

Python benchmark harness with DeepSeek agent/judge clients, memory system adapters, generated JSON cases, analysis scripts, and committed docs for task specs, findings, and design decisions.

Outcome

T4 split-intake results showed extraction-free systems around 95% per-detail recall while mem0 trailed substantially. T2 preview work surfaced silent collateral damage during compound updates.

Reflection

The project taught me that evaluation design is product design. The benchmark only became useful once the tasks resembled realistic memory events instead of clean textbook facts.

No. 003 · Competition · 2026-07-06

Lark Loom

Textrix colloquii

AI Agent · Collaboration · TypeScript · Lark

A Feishu group-chat AI agent that turns fragmented project conversations into docs, task tables, updates, and presentation drafts.

GitHub ↗

Problem

Student project teams often make decisions inside messy group chats. Requirements, deadlines, ownership, and meeting prep get scattered across messages, documents, tables, and slides.

My Role

  • Designed the product direction for a Feishu/Lark group-chat collaboration agent
  • Built the TypeScript monorepo structure across contracts, bot runtime, and skills
  • Implemented the Skill Router direction for recall, summary, archive, requirement docs, task assignment, progress updates, and rehearsal flows
  • Documented product boundaries, Feishu permissions, API constraints, and compliance limits

Product Decisions

  • Let the agent live in the group chat instead of requiring users to switch tools
  • Avoided private 1:1 monitoring and kept the product centered on project group spaces
  • Turned fragmented IM context into structured docs, task tables, and presentation drafts

System Design

pnpm monorepo with contracts, bot, and skills packages. The architecture includes message/card contracts, bot runtime interfaces, Bitable clients, LLM/retriever abstractions, and skill implementations for collaboration workflows.

Outcome

Built as a ByteDance Lark AI Campus Challenge project for the AI product innovation track, with product docs, engineering docs, and a working skill-oriented bot foundation.

Reflection

Lark Loom made the product boundary very concrete: the impressive part is not that an agent can summarize chat, but whether it can do that inside the permission, UI, and workflow limits of a real collaboration platform.

No. 004 · Portfolio · 2026-07-30

Personal Website

Speculum sui

Agent-Friendly · Vanilla JS · Cloudflare · CMS

A PM-style portfolio dashboard with JSON content, pre-rendered HTML, llms.txt surfaces, CMS editing, and a terminal resume.

Live ↗ · GitHub ↗

Problem

A normal portfolio is optimized for humans, while the people and agents reading it increasingly need structured, stable, machine-readable context. I wanted the site to be more than a resume: it should be a living product surface for what I have shipped, what I am building, and how I think.

My Role

  • Designed and built the static portfolio system end to end
  • Created JSON content sources for profile, project board, principles, and contact data
  • Built pre-rendered HTML plus runtime hydration so the same content works with or without JavaScript
  • Added Decap CMS editing, Cloudflare deployment support, llms.txt surfaces, and a terminal-shaped resume CLI

Product Decisions

  • Treated the portfolio as a dashboard instead of a landing page
  • Kept stable card IDs so agents and people can cite projects across conversations
  • Made the site readable through HTML, JSON, llms.txt, llms-full.txt, and npx antares-cv

System Design

Vanilla HTML/CSS/JS, build scripts that generate static artifacts from content/*.json, Decap CMS for browser edits, Cloudflare Pages/Worker support, and a single-file Node CLI that reads the same public content.

Outcome

A content-managed, agent-friendly portfolio where the website, terminal resume, and machine-readable files all share one source of truth.

Reflection

This project is a small statement of taste: if agents are going to read our work, the source material should be deliberate, structured, and still pleasant for humans.
